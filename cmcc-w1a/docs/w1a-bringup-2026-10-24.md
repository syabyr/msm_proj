## 2. GPS / 定位服务（核心问题）

### 2.1 现象

`qmicli` 无法使用 Location 服务（`--loc-*` 失败或超时），表面上像是 qmicli 用法问题。

### 2.2 诊断过程

1. 查 modem 状态：

   ```
   dmesg | grep -E "remoteproc|crash|EFS|watchdog"
   ```

   结果：`4080000.remoteproc`（MSS/modem）在**无限崩溃-恢复循环**中，已累计 crash #66：

   ```
   fs_device_efs_rmts.c:154:[6 ,917504, -1041155264] EFS: rmts_get_buffer api fail
   remoteproc remoteproc0: crash detected ... type fatal error
   remoteproc remoteproc0: recovering 4080000.remoteproc
   ```

   另一种表现形式是启动后约 40 秒：

   ```
   dog.c:1522:Watchdog detects stalled initialization
   ```

   两者是同一个根因（modem 初始化卡在/死于 EFS）。

2. 确认固件与内存布局无误：`mba.mbn` 226176 字节、`modem.mdt` + `modem.bXX` 均可加载，MPSS 段全部落在保留内存 `0x88000000..0x8d4fffff` 内。

3. 确认 QRTR 链路正常：

   - 内核配置：`CONFIG_QRTR=y`、`CONFIG_QRTR_SMD=y`
   - `qcom_smd_qrtr` 驱动已绑定 `remoteproc0:smd-edge.IPCRTR`
   - rpmsg 通道存在：`DATA1-4`、`DIAG*`、`IPCRTR`、`apr_*` 等
   - 说明传输层（AP <-> modem 的 QRTR over SMD）没问题

4. 确认真正缺失的是**RMTFS 服务**：modem 初始化时通过 QRTR 请求 AP 侧 rmtfs 提供 EFS 分区访问（`rmts_get_buffer`），但 AP 上根本没有 rmtfs 守护进程，请求失败 → modem fatal error。

### 2.3 根因

- **modem 固件的 EFS 初始化依赖 AP 侧 rmtfs**。没有 rmtfs 应答，modem 在 `fs_device_efs_rmts.c` 直接报致命错误；remoteproc 自动恢复后再次崩溃，形成循环。
- 偶尔不立即失败时，表现为 `dog.c` 的 40 秒 stall watchdog。
- 附加因素：
  - `drivers/remoteproc/qcom_q6v5_mss.c` 中该驱动 **`rproc->auto_boot = false`**，remoteproc 即使绑定成功也保持 offline，必须显式 `start`。
  - 开机时 remoteproc 在 ~1s 就 probe，此时 rootfs/固件分区尚不可用。
  - 没有 udev，`/dev/disk/by-partlabel/*` 不存在，而 rmtfs `-P` 模式依赖它。

### 2.4 修复步骤（已在设备上执行）

1. 安装 rmtfs（Alpine community，版本 1.3-r0）：

   ```sh
   apk add rmtfs
   ```

2. 备份 EFS 分区（rmtfs 会写这些分区）：

   ```sh
   mkdir -p /root/efs-backup
   dd if=/dev/mmcblk0p11 of=/root/efs-backup/mmcblk0p11.bin bs=64k
   dd if=/dev/mmcblk0p12 of=/root/efs-backup/mmcblk0p12.bin bs=64k
   dd if=/dev/mmcblk0p14 of=/root/efs-backup/mmcblk0p14.bin bs=64k
   dd if=/dev/mmcblk0p18 of=/root/efs-backup/mmcblk0p18.bin bs=64k
   ```

3. 建立 partlabel 链接（rmtfs `-P` 按 GPT 名称查找）：

   ```sh
   mkdir -p /dev/disk/by-partlabel
   ln -sf ../../mmcblk0p11 /dev/disk/by-partlabel/modemst1
   ln -sf ../../mmcblk0p12 /dev/disk/by-partlabel/modemst2
   ln -sf ../../mmcblk0p14 /dev/disk/by-partlabel/fsc
   ln -sf ../../mmcblk0p18 /dev/disk/by-partlabel/fsg
   ```

4. 先启动 rmtfs，再启动 modem：

   ```sh
   rmtfs -P >> /tmp/rmtfs.log 2>&1 &
   sleep 1
   echo start > /sys/class/remoteproc/remoteproc0/state
   ```

   rmtfs 1.3 参数说明：

   | 参数 | 含义 |
   |---|---|
   | `-P` | 使用 `/dev/disk/by-partlabel/<gpt-label>` 访问 EFS 分区 |
   | `-o <dir>` | 改为访问目录下的文件（`modem_fs1` 等） |
   | `-r` | 只读，不写回 EFS |
   | `-s` | 让 rmtfs 负责启动/停止 MSS remoteproc（本方案未用） |

   映射关系（`storage.c` 内置表）：

   | modem 请求路径 | 分区逻辑名 | GPT 标签 |
   |---|---|---|
   | `/boot/modem_fs1` | `modem_fs1` | `modemst1` |
   | `/boot/modem_fs2` | `modem_fs2` | `modemst2` |
   | `/boot/modem_fsc` | `modem_fsc` | `fsc` |
   | `/boot/modem_fsg` | `modem_fsg` | `fsg` |

### 2.6 开机持久化（`/etc/w1a-init.sh` 第 3c 段）

原脚本中已有一段 3c（staging 固件后 `umount` p1、重新 bind remoteproc），但存在两个问题：

1. `umount /mnt/modemfw` 后，`/lib/firmware/modem.*` 符号链接全部悬空；
2. 只 bind 不 start，且没有 rmtfs，modem 无法启动。

已合并为一段完整逻辑（当前生效版本）：

```sh
# --- 3c. modem (MSS) + rmtfs for GPS/location over QRTR.
# The firmware lives on p1 (vfat, image/, ~35MB - too big to bake into
# the rootfs) and is symlinked into /lib/firmware; p1 stays mounted so
# the links resolve.  Without rmtfs answering EFS the modem crashes in
# fs_device_efs_rmts.c during init, and even on success the rproc stays
# offline (driver has auto_boot off) - so serve EFS first, then start.
(
    LOG=/tmp/modem.log
    echo "[modem] start" > $LOG
    mkdir -p /mnt/modemfw /lib/firmware
    grep -q " /mnt/modemfw " /proc/mounts \
        || mount -t vfat -o ro /dev/mmcblk0p1 /mnt/modemfw 2>>$LOG
    for f in /mnt/modemfw/image/modem.* /mnt/modemfw/image/mba.mbn; do
        [ -e "$f" ] && ln -sf "$f" /lib/firmware/$(basename $f) 2>>$LOG
    done
    echo "[modem] firmware staged: $(ls /lib/firmware/modem.mdt /lib/firmware/mba.mbn 2>/dev/null | wc -l) files" >> $LOG

    # rmtfs opens EFS via /dev/disk/by-partlabel/<gpt-label>; no udev here
    mkdir -p /dev/disk/by-partlabel
    ln -sf ../../mmcblk0p11 /dev/disk/by-partlabel/modemst1
    ln -sf ../../mmcblk0p12 /dev/disk/by-partlabel/modemst2
    ln -sf ../../mmcblk0p14 /dev/disk/by-partlabel/fsc
    ln -sf ../../mmcblk0p18 /dev/disk/by-partlabel/fsg
    pkill -x rmtfs 2>/dev/null
    rmtfs -P >> /tmp/rmtfs.log 2>&1 &
    sleep 1
    pgrep -x rmtfs >/dev/null && echo "[modem] rmtfs running" >> $LOG \
        || echo "[modem] ERROR: rmtfs failed" >> $LOG

    # find the mpss remoteproc (index varies: wcnss may be remoteproc0)
    MPSS=""
    for rp in /sys/class/remoteproc/remoteproc*; do
        [ "$(cat $rp/name 2>/dev/null)" = "4080000.remoteproc" ] || continue
        MPSS=$rp
        break
    done
    if [ -z "$MPSS" ] && [ -e /sys/bus/platform/drivers/qcom-q6v5-mss/bind ]; then
        echo 4080000.remoteproc > /sys/bus/platform/drivers/qcom-q6v5-mss/bind 2>>$LOG
        sleep 1
        for rp in /sys/class/remoteproc/remoteproc*; do
            [ "$(cat $rp/name 2>/dev/null)" = "4080000.remoteproc" ] && MPSS=$rp && break
        done
    fi
    if [ -n "$MPSS" ]; then
        echo start > $MPSS/state 2>>$LOG
        n=0
        while [ "$(cat $MPSS/state 2>/dev/null)" != "running" ] && [ $n -lt 15 ]; do
            n=$((n+1)); sleep 1
        done
        echo "[modem] rproc at $MPSS, state=$(cat $MPSS/state 2>/dev/null)" >> $LOG
    else
        echo "[modem] WARN: mpss remoteproc not found" >> $LOG
    fi
) &
```

设计要点：

- **p1 保持挂载**，否则 `/lib/firmware` 中的固件符号链接悬空。
- **先起 rmtfs，再 start modem**：EFS 初始化在 "remote processor is now up" 后约 30ms 就发生。
- **按 rproc 名字定位**，不依赖 `remoteproc0` 序号（WCNSS 与 MSS 的注册顺序可能变化）。
- **显式 `start`**：驱动 `auto_boot=false`。
- 整段放在子 shell 后台执行，失败不会阻塞 sysinit/SSH。

真实重启后的验证（uptime 64 秒，已跨过 40 秒看门狗）：


### 2.7 已知限制与后续

- **实际经纬度仍未拿到**：QMI 服务链路已完全打通（静态查询、`--loc-start`、`--loc-inject-time` 均成功），但引擎相关请求全部无数据：
  - `--loc-get-engine-lock` 始终为 `none`（从未锁定）；
  - `--loc-get-gnss-sv-info`（30/60 秒）超时，`--loc-follow-nmea` 无任何语句；
  - `--loc-get-position-report` 在 120 秒、180 秒超时；
  - 系统时间从 1970 校正为正确时间并 `--loc-inject-time` 后结果不变。

  说明 GNSS 引擎收不到卫星信号。设备目前位于室内；此外该机无 SIM（UIM `no-atr-received`），modem 无法自行下载 XTRA 星历（预测星历服务器为 izatcloud），首次定位会更慢。需要在窗边/室外复测；若室外数分钟仍无卫星，则可判定该机未接 GNSS 天线或硬件不支持。
- `qmicli` 单次调用只允许一个 LOC action（`--loc-start` 与 `--loc-get-*` 不能放在同一进程），而该固件在进程退出后会回收 QMI client，`--client-no-release-cid` 得到的 CID 在下一个进程里会报 `Unknown client`。因此不方便用两条命令跟踪 NMEA。后续可选方案：
  - 室外先 `--loc-start`，再用新的 client `--loc-get-position-report --loc-timeout=120`；
  - 或写一个基于 libqmi 的常驻小程序 / 接 gpsd。
- `CONFIG_QCOM_PD_MAPPER=m`、`CONFIG_QCOM_PDR_MSG=m`、`CONFIG_QCOM_QMI_HELPERS=m`，但 rootfs 没有 modules 目录。本次问题仅靠 rmtfs 即解决；若后续发现 PDR/pd-mapper 相关服务缺失，再把这三个改成 `=y` 重新编译。
- rmtfs 会写 `modemst1/2`、`fsc`、`fsg`；修改前备份在 `/root/efs-backup/`。
- **modem 一启动，直接控制 LPASS 的播放通路即失效**（mainline 已知限制：固件接管 LPASS 硬件块）。同一内核下 modem 不启动时音频播放正常；modem 运行后播放 DMA 冻结、LPASS 中断为 0（采集仍可用）。因此本机音频与 modem/GPS **只能每次开机二选一**，当前默认音频优先（`/root/skip-mpss` 标记）。详见 [w1a-audio-modem-conflict-2026-10-24.md](w1a-audio-modem-conflict-2026-10-24.md)。

## 3. WiFi 开机自启

### 3.1 根因

- 设备使用 **BusyBox init**，OpenRC 从未运行；之前配置的 `/etc/local.d/*.start` 与 `rc-update` 全部无效。
- 真正的启动入口是 `/etc/inittab` → `/etc/w1a-init.sh`。
- 脚本里硬编码使用 `/etc/wpa_supplicant/w1a.conf`，其中 SSID 不是当前环境（N60Pro），导致关联失败。
- 未等待关联完成就请求 DHCP。

### 3.2 修复

- `w1a.conf` 改为 `MYBAYS-2.4G`（PSK 已配置）。
- 启动脚本第 4b 段：WCNSS 重绑定 → 等待 `wlan0` → 启动 `wpa_supplicant` → 轮询 `iw dev wlan0 link` 直到 `Connected to` → 再 `udhcpc`（失败重试）。
- 删除失效的 OpenRC/local.d 配置；备份在 `/root/net-backup-20261024/`。

### 3.3 验证

重启后自动关联，`wlan0 = 192.168.1.183/24`，`ping 153.3.238.127` 约 20–30ms。

### 3.4 系统时间与 NTP 校时（4c 段）

- 现象：设备没有后备电池供电的 RTC，每次启动系统时间都是 **1970-02-01**。
- `/dev/rtc0` 节点存在，但设置时间会失败：

  ```
  hwclock: ioctl 0x4024700a failed: No such device
  ```

  因此 `hwclock -w` 无法把时间写回硬件，不能靠 RTC 持久化。
- 方案：启动脚本新增 4c 段（后台），等 `wlan0` 拿到 DHCP 地址后（最多等 120 秒）执行一次性 NTP 校时：

  ```sh
  timeout 30 ntpd -n -q -p ntp.aliyun.com -p cn.pool.ntp.org
  ```

  BusyBox ntpd 的 `-q` 表示设置时间后退出；失败重试 5 次，日志写入 `/tmp/time.log`。
- 验证：把时钟手动设到 `1970-02-02`，运行该段后数秒内跳到正确时间：

  ```
  ntpd: setting time to 2026-10-24 08:41:55.103822 (offset +1790066512.961800s)
  [time] Sat Oct 24 08:41:55 UTC 2026
  ```

- 影响：WiFi/DHCP 起来之前系统时间仍是错的（日志时间戳、TLS 等）；对 GNSS 可在会话启动后用 `qmicli -d qrtr://0 -p --loc-inject-time` 注入正确时间。
- 注意：NTP 依赖 UDP 123 与 DNS，当前走 wlan0 直连互联网，不依赖主机 NAT。

## 5. 其他排查记录

### 5.1 `git pull` 极慢

- 现象：在 `linux-mainline` 中 `git pull` 数分钟无进展（仓库 6.5G、1180 万对象，但磁盘 180MB/s，不是瓶颈）。
- 原因：DNS/透明代理把 `github.com` 劫持到 `198.10.0.12`、`codeload.github.com` 劫持到 `198.10.0.51`（返回 429）；经本机 HTTP 代理访问 `info/refs` 需 42–64 秒。
- 对照：直连真实 GitHub IP `140.82.113.3` 的 TTFB 约 0.7 秒。
- 本次未改动（仅诊断）。

### 5.2 ALSA 音量

- `sndmix` 的 VALUE 是 **raw 0..124**，映射 -84dB..+40dB（`raw = dB + 84`）。
- `TX` 是采集路径，`RX` 是播放路径；调播放音量应改 `RX1/RX2/RX3 Digital Volume`。
- `amixer` 按名字找不到这些控件（"Unable to find simple control"），需按 numid：

  ```sh
  amixer -c 0 cset numid=<N> <raw>
  ```

- 已按要求将播放音量先调至最大（124），再调至中等（62）；第 3b 段会在开机时应用 mixer 默认值。

## 7. 快速排障清单（modem / GPS）

按顺序执行：

```sh
# 1. 启动段是否跑完
cat /tmp/modem.log

# 2. rmtfs 是否在跑
pgrep -a rmtfs

# 3. modem 状态（running 且不重启）
for r in /sys/class/remoteproc/remoteproc*; do
    echo "$r $(cat $r/name) $(cat $r/state)"
done
dmesg | grep -cE "crash detected"
dmesg | grep -E "EFS|dog\.c|remoteproc0" | tail

# 4. QRTR 服务是否注册（应能看到 Location service / 服务 16）
qrtr-lookup

# 5. QMI 是否可达
qmicli -d qrtr://0 --dms-get-ids
qmicli -d qrtr://0 --loc-start

# 6. 固件与分区链接
ls -l /lib/firmware/modem.mdt /lib/firmware/mba.mbn
ls -l /dev/disk/by-partlabel/
mount | grep modemfw

# 7. 系统时间（正常应在联网后自动校正）
date -u
cat /tmp/time.log
```

如果 `dmesg` 再次出现 `fs_device_efs_rmts.c ... rmts_get_buffer api fail`，优先检查 rmtfs 是否在 modem 启动前已在运行，以及 4 个 partlabel 链接是否指向正确分区。

如果出现 `Watchdog detects stalled initialization`，含义相同：EFS/RMTFS 未及时应答。
